# Gitlog API Connect

이 파일은 프로젝트 API 연결 절차 문서다. 이 경로의 파일 자체는 Codex의 자동 발견 스킬로 등록되지 않는다. 코드 예시와 상세 연결 규칙은 [api-connect.md](./api-connect.md)에 둔다.

대상 기능에 필요한 단계부터 진행하고, 인증·업로드처럼 해당 작업과 무관한 절차는 생략한다. 미확정 계약 때문에 진행할 수 없는 단계는 남겨 두고 의존하지 않는 작업을 진행한다.

## 1. 기본 전제와 작업 범위

**할 일**

- 사용자가 지정한 기능과 기대하는 화면 동작을 확인한다. 범위가 이미 정해졌으면 전체 엔드포인트를 다시 선택하게 하지 않는다.
- 기존 React Router SPA, TanStack Query, axios 구성을 사용한다. 요청하지 않은 기능이나 라이브러리 도입으로 범위를 넓히지 않는다.
- 이번 작업에서 연결할 흐름과 제외할 흐름을 정한다. 기능 구현, 문서 수정, 실제 요청 검증을 구분한다.

**완료 조건**

연결할 기능과 화면 동작, 작업 범위가 명확하고 요청하지 않은 작업이 포함되지 않는다.

## 2. API 명세 확인

**할 일**

- 대상 API의 method·path, path/query parameter, 요청 필드·검증, 응답 본문·헤더, 인증 필요 여부, 오류 조건을 확인한다.
- 성공·오류 판별, 토큰 저장·재발급, 중복 확인, OAuth 콜백, 업로드 방식, 페이지 번호 중 이번 작업에 필요한 계약을 확인한다.
- 여러 요청으로 이루어진 흐름은 호출 순서와 전달할 데이터를 정리한다. 명세 예제를 실제 동작으로 단정하지 않는다.
- 제공된 명세로 해결할 수 없는 경우 빠진 항목만 확인한다. 서버 계약을 추측하거나 명세 주소를 프로젝트 MD 파일에 저장하지 않는다.

**완료 조건**

구현에 필요한 계약과 요청 간 의존 관계가 확인되어 있다. 미확정 항목은 구현을 막는 범위가 구분되어 있고, 확인되지 않은 계약을 확정된 사실로 사용하지 않는다.

## 3. 기존 코드와 Provider 확인

**할 일**

- `rg`와 `rg --files`로 대상 기능의 API·타입·검증·UI·라우트·콜백 사용처를 찾아 읽는다.
- `src/shared/apis/client.ts`의 `api`, `src/app/providers/QueryProvider.tsx`, `src/main.tsx`의 Provider 연결과 환경설정을 확인하고 재사용한다. 환경설정 확인 중 토큰·비밀번호를 출력하지 않는다.
- 가입·로그인은 `SignupForm`, `LoginDialog`, `LoginHandler`, `useLayoutAuth`와 레이아웃의 호출 관계를 확인한다. 다른 기능도 저장 결과를 사용하는 호출자와 표시 데이터의 소유권을 확인한다.
- 실제 미리보기 상태와 구현된 공통 처리를 구분한다. 동기 결과를 전제로 성공을 판단하는 콜백 등 함께 수정할 호출자를 찾는다.

**완료 조건**

재사용할 클라이언트·Provider와 변경할 파일·호출자가 확인되어 있다. 어떤 미리보기 상태를 서버 데이터로 바꿔야 하는지 파악되어 있다.

## 4. 연결 방식 결정

**할 일**

- 조회는 `useQuery`, 사용자 작업으로 시작하는 변경은 `useMutation`으로 정한다. OAuth 이동은 확인한 브라우저 이동 계약에 맞춘다.
- API 함수·Query 훅·Query Key는 `src/features/{feature}/api/`, 기능 전용 타입·클라이언트 상태는 `model/`, 순수 검증·변환은 `lib/`, 화면은 `ui/`에 둔다.
- 인증 API는 `src/features/auth/api/`, 여러 기능이 공유하는 타입은 `src/shared/types/`에 둔다. 이번 기능에 필요한 파일만 추가한다.
- 서버 데이터로 전환할 상태와 유지할 폼·다이얼로그·페이지 조건·로컬 이미지 상태를 구분한다. 조회 시점, 인증 준비 조건, 변경 후 갱신할 캐시를 정한다.

**완료 조건**

요청의 실행 시점, 코드 위치, 상태 소유권과 캐시 갱신 대상이 정해져 있다. 서버 상태를 미리보기 상태와 중복 관리하는 계획이 없다.

## 5. 요청·응답 타입 작성

**할 일**

- 확인한 명세로 요청·응답 타입을 작성하고 공통 응답 본문과 기능별 데이터를 구분한다. 불명확한 값은 `unknown`으로 두고 필요한 확인을 진행한다.
- 폼 상태와 요청 타입을 분리한다. 비밀번호 확인이나 로컬 이미지 미리보기처럼 화면 전용 값은 서버 요청에 포함하지 않는다.
- 날짜는 요청·응답에서 문자열로 유지한다. 서버와 화면의 필드명·id 타입이 다르면 필요한 순수 변환 함수를 작성한다.

**완료 조건**

요청·응답 형태와 필수·선택 필드가 명세에 맞고, 화면 전용 값이 요청에 섞이지 않는다. 필요한 데이터 변환과 미확정 타입이 구분되어 있다.

## 6. API 함수 작성

**할 일**

- 기능별 API 함수에서 공통 `api`로 요청한다. baseURL과 경로의 조합을 확인하고 query parameter는 axios의 `params`로 전달한다.
- API 함수는 axios 응답 본문을 반환한다. 공통 본문의 기능 데이터 추출은 Query 훅에 두고 UI에서 반복하지 않는다.
- HTTP 오류의 reject 상태를 유지한다. HTTP 성공 응답 안의 업무 오류도 확인한 계약에 맞춰 실패로 처리하고, 오류를 목 데이터로 대체하지 않는다.
- 업로드가 포함되면 URL 발급·외부 저장소 전송·최종 URL 등록을 구분한다. 서명 조건과 최종 URL 계약을 확인하고 저장소 요청에 백엔드 토큰을 보내지 않는다.

**완료 조건**

요청 method·path·parameter·본문과 반환 형태가 명세에 맞고, 실패가 호출자에게 전달된다. 업로드가 포함되면 각 단계와 실패 복구 경로가 확인된 계약에 따라 구성되어 있다.

## 7. 인증과 토큰 처리

**할 일**

- 대상 흐름에 인증이 필요한 경우 적용한다. 저장 정책을 확인하고 토큰 읽기·쓰기·삭제와 인증 헤더 주입을 공통 인증 관리 코드로 모은다.
- 로그인 성공·인증 복원 시 내 정보 조회와 연결한다. 카카오 인증은 콜백의 기존 회원·신규 회원 구분과 추가 가입 전달 계약에 맞춘다.
- 로그인 실패를 토큰 만료로 취급하지 않는다. 확인된 만료 오류만 재발급하고 동시 요청은 한 번의 재발급을 공유하게 한다. 재발급 요청의 반복과 원래 요청의 무한 재시도를 막는다.
- 재발급으로 받은 두 토큰을 함께 갱신한다. 재발급 실패·로그아웃·계정 변경 시 인증 정보와 사용자별 캐시를 정리한다.

**완료 조건**

대상 흐름의 인증 헤더·토큰 저장·복원·재발급·정리가 확인된 정책대로 연결되어 있다. 재발급이 반복되지 않고 이전 사용자의 정보가 남지 않는다. 필요한 인증 계약이 미확정이면 이 단계를 완료로 표시하지 않는다.

## 8. React Query 훅과 캐시 처리

**할 일**

- 기능별 Query Key를 배열로 구성하고 목록·상세·id·필터·페이지·인증 문맥 등 결과를 바꾸는 조건을 포함한다.
- Query 훅에서 공통 응답의 기능 데이터를 추출하고 필요한 화면 모델 변환을 적용한다. 필요한 id나 인증이 준비된 경우에만 조회한다.
- 변경 성공 시 관련 캐시를 갱신하거나 무효화한다. 공개·인증 조회와 계정 변경에 따른 캐시 정리를 반영한다.
- 인증 실패·입력 오류를 반복 재시도하지 않는다. 변경 요청의 자동 재시도는 중복 처리 위험과 서버 계약에 맞춰 결정한다.
- `queryFn`에서 라우팅·다이얼로그 조작을 하지 않는다.

**완료 조건**

훅이 화면에 필요한 데이터를 반환하고 조회 조건과 재시도 정책이 정해져 있다. 변경 후 관련 화면의 데이터가 갱신되며 사용자·조건이 다른 캐시를 잘못 재사용하지 않는다.

## 9. UI 연결

**할 일**

- UI에서 기능 훅을 사용하고 화면·콜백을 비동기 요청 결과에 연결한다. 동기 boolean을 Promise로만 바꾸고 호출자의 즉시 성공 판정을 남겨 두지 않는다.
- 로딩·오류·빈 결과·성공 상태를 표시한다. 조회 대기와 실제 네트워크 로딩을 구분하고 입력 오류는 해당 입력 또는 폼에 연결한다.
- 제출 중 중복 요청을 막고 성공 표시·화면 이동·다이얼로그 종료는 서버 응답 이후에 수행한다.
- 연결한 서버 데이터를 미리보기 상태에서도 별도로 갱신하지 않는다. 폼·로컬 이미지 상태는 필요한 동안 유지하고 실패 시 재시도·재선택 등 복구 동작을 제공한다.

**완료 조건**

화면과 모든 호출자가 실제 요청 결과를 기준으로 동작한다. 즉시 성공 판정과 중복 제출이 없고, 오류·빈 결과·복구 동작이 사용자에게 표시된다.

## 10. 검증과 결과 보고

**할 일**

- 코드·빌드 설정 변경 후 `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm run build`를 실행한다. 문서만 변경하면 대상 문서의 포맷·참조·내용 일관성을 확인한다.
- 연결 범위의 성공·실패 흐름과 위험한 로직의 경계 조건을 확인한다. 해당되는 인증 만료·재발급 실패·계정 변경·업로드 및 등록 실패도 검증한다.
- 실제 서버 데이터를 바꾸는 검증은 요청된 작업 범위와 환경에서 진행한다. 명세 확인이나 정적 검증을 실제 요청 검증으로 간주하지 않는다.
- 완료 보고에는 연결한 기능, 선택한 방식과 근거, 검증 방법·결과, 남은 미확정 계약과 검증하지 못한 흐름을 구분해 적는다.
- 구현 현황과 요청·검증 결과는 완료 보고로 전달하고, 이 문서와 `api-connect.md`에 작업 기록으로 누적하지 않는다. 미확정 계약은 `api-connect.md`의 해당 목록에만 정리한다.

**완료 조건**

변경 범위의 검증 결과가 확인되어 있고 실패·미실행 항목과 남은 제약이 보고되어 있다. 구현하지 않았거나 검증하지 못한 흐름을 완료로 표시하지 않는다.
