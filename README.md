## ⚙️ 기능 요구사항

백엔드 스웨거 : https://blog.leets.land/swagger-ui/index.html

### 회원가입

- 사용자는 이메일 주소 또는 카카오 OAuth를 통해 회원가입을 진행할 수 있어야 합니다.
- 사용자는 비밀번호를 생성하여 회원가입을 진행할 수 있어야 합니다.
- 사용자는 프로필사진을 등록하며 회원가입을 진행할 수 있어야합니다.
- 사용자가 입력한 이메일 주소와 닉네임은 시스템에 이미 등록되어 있지 않아야 합니다.

### 로그인

- 사용자는 등록한 이메일 주소 또는 카카오 로그인을 이용하여 로그인할 수 있어야 합니다.
- (토큰 방식으로 구현시) refresh token을 통해 새로운 access token을 발급받을 수 있어야 합니다.
- 토큰은 브라우저에 cookie / storage 중 원하는 방식을 골라 선택하신 후 저장 해 두셔야 합니다.

### 게시물

- 사용자는 로그인을 하지 않고도 게시물을 조회할 수 있어야 합니다.
- 사용자는 로그인을 진행해야 게시물을 작성할 수 있어야 합니다.
- 사용자는 자신의 게시물만 수정, 삭제할 수 있어야 합니다.
- 게시물은 페이지네이션이 가능해야 합니다.
- 게시물 리스트는 한 페이지에 10개까지 보여야 하며, 초과 시 다음 페이지에서 볼 수 있어야 합니다.
- 게시물 조회시 댓글도 모두 조회할 수 있어야 합니다.
- 게시물 작성 시, 텍스트와 이미지의 contentOrder도 트래킹 할 수 있어야 합니다.
  - 추후 READ 기능 구현 시 텍스트 / 이미지의 순서를 맞추어 렌더링 할 수 있게 해야 합니다.

### 댓글

- 사용자는 로그인을 하지 않고도 댓글을 확인할 수 있어야 합니다.
- 사용자는 댓글을 입력 하고 싶으면 로그인을 해야 합니다.
- 사용자는 자신의 댓글만 수정, 삭제할 수 있어야 합니다.

### 유저

- 사용자는 닉네임, 비밀번호, 프로필 사진을 변경할 수 있어야 합니다.
- 사용자는 자신의 정보를 조회할 수 있어야 합니다.

### 이미지

- 이미지는 Pre-Signed Url 방식으로 업로드 할 수 있어야 합니다.

### 반응형 디자인

- Figma에서 제공한 디자인 가이드에 맞춰 데스크톱·모바일 환경에 모두 대응하는 반응형 UI를 구현해야 합니다.

## 로컬 실행

1. 의존성을 설치합니다: npm install
2. .env.example을 .env.local로 복사하고 API 주소를 설정합니다.
3. 개발 서버를 실행합니다: npm run dev

## Lighthouse 측정

Chrome 개발자 도구(F12)의 Lighthouse에서 프로덕션 빌드를 직접 측정합니다.

### 1. 측정할 빌드 실행

`.env.local`에 실제 API 연결을 설정하고, 실행 중인 개발 서버는 `Ctrl+C`로 종료합니다.
프로젝트 루트에서 아래 명령을 순서대로 실행합니다.

```sh
npm run build
npm run preview -- --host localhost --port 3000 --strictPort
```

`npm run build`가 만든 `dist/`를 preview 서버로 제공합니다.
브라우저에서 `http://localhost:3000`을 열고 게시물·이미지가 정상적으로 표시되는지 확인합니다.
API 오류 화면이나 빈 목록을 측정한 결과는 실제 게시물이 표시된 화면과 구분합니다.
환경 변수나 코드를 수정했다면 다시 빌드하고 preview 서버를 재시작합니다.

### 2. F12에서 Lighthouse 실행

1. Chrome에서 측정하려는 페이지를 엽니다.
2. `F12`를 누르고 **Lighthouse** 탭을 선택합니다. 탭이 숨겨져 있으면 `>>` 메뉴에서 찾습니다.
3. 모드는 **Navigation(탐색)**, 기기는 **Mobile(모바일)**로 선택합니다.
4. **Performance(성능)**, **Accessibility(접근성)**, **Best Practices(모범 사례)**, **SEO** 네 항목을 선택합니다.
5. **Analyze page load(페이지 로드 분석)**를 눌러 보고서가 나올 때까지 기다립니다.
6. 같은 페이지를 같은 설정으로 3회 측정해 각 항목의 중앙값을 기록합니다.
7. 기기를 **Desktop(데스크톱)**으로 바꾸고 같은 과정을 반복합니다.

브라우저 언어·버전에 따라 버튼 이름은 조금 다를 수 있습니다.
확장 프로그램의 영향을 줄이려면 확장 프로그램이 비활성화된 시크릿 창에서 공개 페이지를 측정합니다.
로그인이 필요한 화면은 별도로 로그인한 뒤 측정하고, 로그아웃된다면 Lighthouse 설정의
**Clear storage(저장소 지우기)**를 해제해 세션이 유지되는지 확인합니다.
Navigation 모드는 페이지를 새로 불러오므로 로그인 다이얼로그처럼 일시적으로 연 UI는 닫힐 수 있습니다.

### 3. 측정 대상과 결과 기록

기본 측정 대상은 홈(`/`), 가입 방식 선택(`/mypage/signup`), 이메일 가입(`/mypage/signup/email`)입니다.
이미지가 포함된 공개 게시글 상세(`/posts/실제게시글ID`)도 측정합니다.
로그인 후 화면은 로그인 상태와 측정한 URL을 함께 기록합니다.

각 페이지의 모바일·데스크톱 결과에서 **네 항목 모두 중앙값 90점 이상**을 목표로 합니다.
예를 들어 3회 점수가 88, 95, 92점이면 중앙값은 92점입니다.

| 측정일     | 페이지 URL             | 기기    | 성능      | 접근성    | 모범 사례 | SEO       |
| ---------- | ---------------------- | ------- | --------- | --------- | --------- | --------- |
| YYYY-MM-DD | http://localhost:3000/ | Mobile  | 직접 기록 | 직접 기록 | 직접 기록 | 직접 기록 |
| YYYY-MM-DD | http://localhost:3000/ | Desktop | 직접 기록 | 직접 기록 | 직접 기록 | 직접 기록 |

보고서의 저장/내보내기 기능으로 HTML 또는 JSON을 저장하고, 결과를 PR에 첨부합니다.
Chrome·Lighthouse 버전, 측정 모드, 로그인 여부와 함께 낮은 점수의 원인·개선 내용을 기록합니다.
비교할 때는 같은 PC·브라우저·기기 설정을 사용하고 다른 무거운 작업은 종료합니다.
배포 후에는 실제 배포 URL에서도 다시 측정합니다. API·이미지 응답 시간과 캐시가 달라질 수 있습니다.
