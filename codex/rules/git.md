# Git

브랜치, 커밋, PR을 만들거나 변경할 때 적용합니다.

## 안전 원칙

- 작업 전 `git status`와 현재 브랜치를 확인합니다.
- 사용자가 작성한 변경과 현재 작업의 변경을 구분합니다.
- 현재 작업과 무관한 파일은 수정, 스테이징, 커밋하지 않습니다.
- `git add .`보다 대상 파일을 명시해 스테이징합니다.
- 사용자가 정확한 이름을 지정한 경우에만 새 브랜치를 만듭니다.
- 사용자의 명시적인 요청 없이 기존 커밋을 amend, rebase, reset하거나 force push하지 않습니다.
- 충돌 해결 시 어느 한쪽 변경을 임의로 버리지 않습니다.
- `.env`와 비밀값, 개인 설정 파일을 커밋하지 않습니다.

## 커밋 단위

- 하나의 커밋에는 리뷰와 되돌리기가 가능한 하나의 논리적 변경만 담습니다.
- 파일 수가 아니라 변경 목적을 기준으로 커밋을 나눕니다.
- 설정, 공통 기반, 기능 구현, 리팩터링이 독립적으로 검토 가능하면 분리합니다.
- 같은 기능을 완성하는 코드와 필요한 타입·스타일·생성 결과는 함께 커밋할 수 있습니다.
- 단순히 커밋 수를 늘리기 위해 강하게 연결된 변경을 나누지 않습니다.

## 커밋 메시지

형식은 `<type>: <한국어 subject>`를 사용합니다.

- `feat`: 사용자에게 보이는 기능 또는 컴포넌트 추가
- `fix`: 잘못된 동작 수정
- `refactor`: 동작을 유지하는 구조 개선
- `style`: 포맷처럼 동작과 무관한 코드 표현 변경
- `docs`: 문서 변경
- `test`: 테스트 추가 또는 수정
- `chore`: 도구, 의존성, 설정 변경
- `perf`: 성능 개선
- `ci`: CI 설정 변경
- `revert`: 기존 변경 되돌리기

subject는 변경 결과가 드러나는 한국어로 작성하고 마침표를 붙이지 않습니다.

예시:

- `feat: 공통 UI 페이지네이션 컴포넌트 구현`
- `fix: 입력창 포커스 테두리 색상 수정`
- `refactor: 컴포넌트 선언 형식 통일`
- `docs: Codex 프로젝트 지침 추가`

실제 커밋 전에는 다음 내용을 사용자에게 보여주고 확인받습니다.

- 커밋별 포함 파일과 변경 목적
- 실행한 검증과 결과
- 제안하는 한국어 커밋 메시지

확인받은 내용이 바뀌면 다시 확인받습니다.

## 커밋 전 확인

- 스테이징된 diff에 현재 작업만 포함되었는지 확인합니다.
- 관련 타입 검사, 린트, 빌드 또는 포맷 검사를 실행합니다.
- 생성 파일은 원본 설정이나 라우트 변경과 함께 갱신되었는지 확인합니다.
- 디버그 코드, 임시 UI, 불필요한 주석이 남지 않았는지 확인합니다.
- 검증하지 못한 항목은 숨기지 않고 보고합니다.

## Pull Request

- 제목과 설명은 한국어로 작성합니다.
- 제목은 최종 변경의 목적을 짧게 표현합니다.
- 설명에는 문제와 변경 결과, 주요 구현, 검증 결과를 포함합니다.
- UI 변경은 필요할 때 전후 화면이나 확인 방법을 제공합니다.
- 관련 없는 변경 이력이나 중간에 폐기한 접근은 설명에서 제외합니다.
- 리뷰 피드백으로 지속 가능한 규칙이 확인되면 관련 `codex/rules` 문서를 함께 갱신합니다.
